# 搜索流水线优化路线图

> 最后更新：2026-05-04

---

## 一、当前检索架构

```
用户查询
  ├── Qdrant 向量检索 (bge-large-zh-v1.5, 1024维, Cosine)
  ├── OpenSearch 文本检索 (SmartCN 中文分词, BM25)
  ▼
  RRF 倒数排名融合 (K=60)
  ▼
  返回 Top-K 结果
```

- **嵌入模型**: `BAAI/bge-large-zh-v1.5`（1024维，中文开源第一梯队）
- **向量库**: Qdrant
- **文本库**: OpenSearch 2.11.0 + analysis-smartcn
- **知识图谱**: Neo4j（`Entity` → `RELATES_TO` 关系网络）
- **融合**: RRF (Reciprocal Rank Fusion)，替代了原来错误的加权求和

| # | 改进项 | 效果 | 状态 |
|---|--------|------|------|
| 1 | **中文分词器** — `standard` → SmartCN | 中文不再逐字拆分，BM25 搜索从"不能用"变"能用" | ✅ 已完成 |

| 4 | **兜底模型清理** — 移除 `all-MiniLM-L6-v2` | 不再静默回退到纯英文嵌入模型，配置错误直接报错 | ✅ 已完成 |

## 四、待实施的优化（按优先级）

### 🟢 Tier 1：高收益、低投入

#### 4. retriever.py 接入 hybrid search
- **文件**: `analyzer/app/knowledge_point_retriever.py:236`
- **现状**: 调用 `search_with_scores`（纯向量），漏掉了 OpenSearch
- **改动**: 改为 `hybrid_search_with_scores`，让 `/api/ask` 同时享受文本匹配
- **收益**: `/api/ask` 路径补齐 BM25 文本匹配，命中率提升
- **投入**: 极低（一行代码改动）

#### 6. OpenSearch 分数归一化修复
- **文件**: `analyzer/app/vector_db.py:438`
- **现状**: `score/max_score` 导致差结果也能得满分
- **改动**: 改用 sigmoid 归一化
  ```python
  normalized = 1.0 / (1.0 + math.exp(-raw_score / scale))
  ```
- **收益**: 分数区分度更好，不会出现"弱结果拿满分"
- **投入**: 低

#### 7. Post-filter → Pre-filter
- **文件**: `analyzer/app/knowledge_point_retriever.py:613-668`
- **现状**: `package_id` 和 `knowledge_point_id` 过滤在召回之后做
- **改动**: 把 metadata filter 直接传给 Qdrant 的 `Filter` 和 OpenSearch 的 `filter` 子句
- **收益**: 后端在检索时就过滤，不浪费召回配额
- **投入**: 低

### 🟡 Tier 2：中收益、中投入

#### 3. BGE Reranker 重排序
- **现状**: 粗排（向量+BM25）结果直接返回，无精排
- **方案**: 搭配 `BAAI/bge-reranker-v2-m3` 做 Cross-encoder 重排
- **流程**: `召回（向量+BM25, top30）→ Reranker精排 → 返回top5`
- **收益**: 典型可提升 10-20% 命中率
- **代价**: 
  - 额外加载一个模型（~2GB 内存）
  - 每次重排需要 30 轮 forward pass（约 200-500ms）
- **注意**: 需要评估 16GB 机器能否承受（目前已跑 PostgreSQL + Qdrant + OpenSearch + Neo4j + API）

#### 5. 图谱检索从 CONTAINS 改为向量语义检索
- **文件**: `analyzer/app/graph_db.py:52`
- **现状**: `toLower(root.name) CONTAINS toLower(keyword)` 只能字面匹配
- **方案**:
  1. 对图谱中所有 `Entity.name` 做 embedding（复用 bge-large）
  2. 存入 Qdrant 的独立 collection
  3. 检索时用 query embedding 做语义搜索找到相关节点
  4. 再从节点出发做图遍历
- **收益**: "函数单调性" 能命中 "导数与单调性" 节点，不再受限于字面

#### 8. 图谱分数公式校准
- **文件**: `analyzer/app/graph_db.py`
- **现状**: `0.45 + hits*0.18 + 0.2/depth` 无数据依据
- **方案**: 用标注数据做网格搜索，找最优权重组合
- **投入**: 需要先建立评测数据集

### 🔵 Tier 3：大改动

#### 10. LLM Query 扩展/改写
- **场景**: 短查询、口语化查询（如"集合那块儿"）命中差
- **方案**: 检索前先走轻量 LLM 生成关键概念词、同义词、教材标准表达，再拼入检索 query
- **代价**: 每次搜索多一次 LLM 调用（约 200-500ms）

#### 11. 真正的 GraphRAG
- **现状**: "GraphRAG" 命名但实际不查 Neo4j
- **方案**: 从 Neo4j 走多跳遍历拿结构化证据（而非仅做关键词匹配）
- **流程**: `query → 向量找到入点实体 → Neo4j 多跳遍历 → 收集关联知识点 → 作为证据返回`

#### 12. 搜索调用次数优化
- **现状**: 每题最多 60+ 次 hybrid search 调用
- **方案**: 合并同类型的 batch query，或做缓存

#### 评测数据建设
- 标记 100-200 条 query 的 ground truth，用于校准所有融合权重和评估改进效果
